# Text rendering (`use8bitfont 0` GDI font path)

How `div.exe` draws text with a Windows font, and what the mod's font hook changes. Bitmap font file layout and families (`use8bitfont 1`): `file-formats.md`. Addresses: verified 1.0062A `div.exe` (`game-version.md`).

## Which texts use which path

`use8bitfont` in `config.lcl` (or the mod's font mode, below) switches **all** game text at once: with `1` the game opens all 61 `fonts/*.fnt` files at startup and no GDI font; with `0` it opens **no** `.fnt` file and instead creates **one GDI font per bitmap font** – the same list of 61 in the same order (fixed table in `div.exe`), every one as face **"SimSun"** (a Chinese system font – the mode was evidently made for the Chinese version), weight 600, `ANSI_CHARSET`, height per family. Measured with the font log (`LogLevel=debug`) in DE and EN, identical in both.

## Path

- The font class (`CDivinityFont`, source `.\font\Font.cpp` per assert strings) has two GDI constructors: one takes face name, height, weight, italic and underline and calls `CreateFontA` (around `0x494330`); the other takes a full `LOGFONTA` and calls `CreateFontIndirectA` (around `0x493E20`; the 61 game fonts come through here, return address `0x493E39`). A third function (around `0x499040`) lists installed fonts with `EnumFontFamiliesExA`.
- The font descriptors carry two face names (tried in order, then any font of the character set via `EnumFontFamiliesExA`), height, weight 600 and a color; the GUI code (`.\BMGUI\Bmgui.cpp`) can read an optional `fontlist.txt` (not present in the Steam installation). Without it the faces are "SimSun". A list of the enumerated fonts can be written to `ttfonts.lst`.
- `CreateFontA("Arial Bold", 18, …)` (around `0x5A84D1`) is the only face name in `div.exe`; it was not called up to character creation. On Windows that request gives **Arial** – there is no family named "Arial Bold".
- **Timing:** all 61 fonts are created within the first ~200 ms of the process, long before the game window exists – a hook must be in place when the mod is loaded (the deferred start is too late).
- The font is selected into a **memory DC** (`CreateCompatibleDC`, based on the screen DC from `GetDC(NULL)`). Nothing is drawn with `TextOut`/`ExtTextOut`, and **no GDI call touches a DirectDraw surface** – `div.exe` does not import DirectDraw at all.
- Each character is rasterized once, on first use, with `GetGlyphOutlineA` in 8-bit gray mode (`GGO_GRAY8_BITMAP`, 65 levels). The gray levels are mapped through a 65-entry color ramp (the family's color) to 16-bit pixels (RGB565 or RGB555 depending on a game global that matches the renderer's 565 flag) and converted into the game's own sprite format. The result is cached per byte value (table of 256 entries); drawing is then done by the game's 2D sprite blitter into the back buffer (`renderer-d3d6.md`).
- Metrics: the space character is measured at creation (`GetGlyphOutlineA` with `GGO_METRICS`); each cached glyph keeps its black-box size, origin and advance.
- **Font object and glyph:** full layout in "Glyph table, drawing and layout" below. GDI specifics: the GDI part at `+0x00` holds the `HFONT`, the memory DC at `+0x08` and a `MAT2` at `+0x0C`; `+0x0C` of the font object is the game's own `lfHeight` (not the one the hook passes to GDI).
- **Glyph creation** (around `0x493F80`, `__thiscall`, character as argument): returns nothing for the space and for a cached glyph; otherwise asks `GetGlyphOutlineA` for the buffer size and **creates no glyph if the size is 0 or the call fails** – the table entry stays null, exactly like a character missing from a `.fnt`.
- **"Has glyph" check** (around `0x4939F0`, `__thiscall`, character and a "create" flag): true for the space or a cached glyph; for a GDI font with the flag set it creates the glyph first. Its only caller is the character handler of the text field (below).
- **Pair spacing** (around `0x494670`, `__thiscall`, previous and next character, returns the distance in pixels; cached per pair in a 256×256 byte table, `0xFF` = not computed): the game places the next glyph at the previous glyph's advance + origin x and slides it left one pixel at a time until its pixels would overlap the previous glyph's (tested at the same height and one pixel up and down), then takes the last free position – so neighbors may **touch**. The overlap test misses the glyphs' bottom row, so feet can even be covered (Tahoma Bold "Li": the "i" stands on the foot of the "L" and the word reads "li"). Exceptions: after a space the space width; quotes and underscore are not slid. The bitmap fonts are drawn for this (no feet, dark anti-aliased edges); with a Windows font crisp shapes touch – in Tahoma Bold 12 px the period after "1" lands right of its foot and both read as one line ("7147" instead of "71.47"). The period is drawn; its pixels merge. The value returned when nothing touches, advance + origin x, counts the left bearing twice: glyphs are drawn at pen + origin x (draw function around `0x4944E0`), so the font's own spacing is the advance alone.

## Glyph table, drawing and layout (both paths)

Both font kinds end in the same structures, so everything here holds for `.fnt` and GDI fonts alike. This is the basis for the target text renderer (PLAN.md Decisions).

- **Font object** (0x44 bytes, constructor around `0x493A30`): `+0x00` GDI part (null for `.fnt`), `+0x04` pair-spacing cache (64 KB, `0xFF` = not computed), `+0x08`–`+0x13` the 12 header bytes of the `.fnt` file (table size, **line height at `+0x0C`**, glyph count; GDI: `+0x0C` = the game's `lfHeight`), `+0x14` table of 256 glyph pointers, `+0x18` the `.fnt` file block (null for GDI), `+0x1C` a built-in space glyph, `+0x2C` **space width** (i16), `+0x34` flag "store GDI glyphs as full rectangles" (0), `+0x38`–`+0x3D` colors, `+0x3E` text-field cursor color (u16), `+0x40` layout variant flag copied from settings `+0x130` (a second set of the same measure/draw functions; it changes only how lines are cut).
- **`.fnt` loading** (around `0x493D50`; the function at `0x496750` only queues the file name, the files are opened when the font list is turned into font objects around `0x4958C0`): checks `ML_FONT_01`, copies the header into `+0x08`, reads the rest of the file as one block into `+0x18`, uses the block's first 1 KB directly as the glyph table and turns every offset into a pointer (aliases into the pointer of the glyph they name). Each **glyph record in the file is already the in-memory glyph** (layout below, `file-formats.md`); the loader only turns the sprite's row offsets into pointers. No pixel conversion – the pixels stay RGB565 as stored. If the file has no space glyph, entry 0x20 points to the built-in one and the space width is set to **6 px** for every bitmap font. A second, older loader (fixed 224 glyphs from 0x20, 20-byte metrics) handles files without the `ML_FONT_01` tag; none of the shipped files uses it.
- **Glyph** (both kinds): `+0x00`/`+0x04` black-box width/height (GDI only; in `.fnt` files these 8 bytes are the constant marker and unused), `+0x08` origin x, `+0x0C` origin y (the glyph is drawn at pen y minus this value; `.fnt` stores minus the top row, GDI the font ascent shifted so that the baseline lies at line top + `+0x0C` − 1), `+0x10` advance (i16), `+0x12` vertical advance (i16, 0), `+0x14` character code (i16), `+0x16` **sprite**.
- **Sprite** (the game's general 2D sprite format, also used for its other images): u32 total size, u32 offset of the pixel block, u16 width, u16 height, one row entry per row (span count, pointer to the row's first pixel, spans of x and length, span count again), then the RGB565/555 pixels of all spans. Pixels outside the spans are transparent; there is **no per-pixel alpha**. The GDI path builds it from a full 16-bit rectangle in which the value 0 means transparent (a converter around `0x559750` packs the non-zero runs; a second one around `0x5587F0` makes one full span per row), and it maps any glyph pixel that would come out as 0 to 1 so that it stays visible.
- **Lifetime:** the font destructor (around `0x493B20`) frees only the file block for a `.fnt` font (the glyphs live inside it); for a GDI font it frees every table entry except the space and the table itself, with the game's heap. Fonts are created once at startup.
- **Drawing:** a character is drawn at pen x + origin x, pen y − origin y by queueing its sprite with the renderer's sprite container (`DllSlashedGetInfo(0)`, `CSpriteContainerImp`, vtable `+0x28`: sprite, x, y, a sort value and flags). The container collects the requests in a list (`COverlay` in `slash1.dll`, 32 bytes per entry), sorts it and draws it at the end of the frame. The request is dropped only if the sprite lies completely off screen – a glyph is **not clipped to its line**. Per-sprite flags exist (a sibling method sets a fixed 50 % translucency for one flag bit); per-pixel blending does not. A second path (around `0x494580` → `0x556A80`) copies the span pixels opaquely into a 16-bit buffer, clipped to the buffer – used for panels the game pre-renders with text and then turns into one sprite (e.g. around `0x523D00`).
- **Nothing above the line top in menu entries and the diary title (T1.17-W):** own glyphs whose ink reaches above the top of their line (origin y > 0) lose exactly those rows in the main menu and its pages (`fontbig24*`/`fontbig36*`: umlaut dots of "ZURÜCK", "ÜBERNEHMEN", the ascenders of Uncial Antiqua's d, h, k, l) and in the diary title (`diary_head_*`: the Ä's dots). The sprite container itself drops only sprites that lie completely off screen (`slash1.dll`, its `+0x28` method checks the screen size only), so the cut comes from the game side – probably these texts go through the buffer path above, whose buffer starts at the line top (not traced further). The original bitmap fonts never reach above the line top (every glyph's top row ≥ 0, `fontbig36` capitals from row 2, diary capitals from row 3–4). The mod keeps the ink below it (`[Family.*] TopFit`). How much room there is: `fontbig36` capitals start at row 2, `diary_head_1024` at row 4 – Uncial Antiqua's d/h/k/l and Ü reach 7 px above that (its left Ü dot touches the U's arm), Almendra SC's Â/Ê/Î/Ô/Û 6 px and its Ä 3 px after moving close.
- **Layout:** measuring and line breaking (around `0x494DC0`, `0x495260`, `0x495380`, `0x494F50`) add the pair spacing (or the advance) per character and the space width `+0x2C` per space; nothing reads a glyph's height. The **line pitch comes from the font's `+0x0C`**, read directly by the callers: several list and text views use `+0x0C` + 1 (the largest of the fonts involved, around `0x4F1170`, `0x4F6AC0`, `0x4F6EF0`, `0x4F7230`, `0x4F8540`), others add `+0x0C` per line (around `0x470800`, `0x51A170`, `0x55F030`), and some panels size themselves as lines × `+0x0C` plus a margin (around `0x523040`, `0x530AB0`). A text line is skipped only when its y is more than two line heights outside the target.

**Consequences for own glyphs:**

- **Larger glyphs are possible:** the sprite size is free, drawing does not clip to the line, and line breaking follows the real advances, so wider text wraps earlier and panels sized by line count grow. Vertically, neighbors overlap unless `+0x0C` grows too; raising `+0x0C` widens the pitch wherever the layout reads it (and moves the GDI baseline, but not the origin of an own glyph). Measured (T1.13-W, DE + EN): the load list, letters and books take the wider pitch, and the reading window's **page break follows** – the text simply spreads over more pages. Families not tried yet: `open-questions.md`.
- **Ways to feed own glyph data:** (1) the GDI path as now – one face per font, colors only as the two-color ramp; (2) answering `GetGlyphOutlineA` with own coverage – any rasterizer, but still the two-color ramp; (3) **an own glyph table:** after a font object is created, replace all 256 table entries with own glyphs (own origin, advance, sprite in full 16-bit color per pixel) and set `+0x0C` and `+0x2C` as needed. (3) carries every style (color profile, rim, gloss across the strokes, texture) and works with the bitmap path as shipped (`use8bitfont 1`): no GDI font, no font mode, no SimSun or Proton font substitution, the code page decides only which character goes into which byte slot. In the bitmap path the destructor frees only the file block, so the own glyphs stay the mod's memory; in the GDI path the game would free them with its own heap.
- **Glyph renderer (`src/fonts/glyphtable.cpp`, `families.cpp`; `[Fonts] Renderer=glyphs`, default):** hooks the font file loader (around `0x494440`, `__thiscall` on the font object with the file path, signature of its first 48 bytes, fallback RVA `0x94440`). After the original has loaded a file it maps the stem to its family (interface `font{n,gra,red,b,go,or,yel,gr}1–5`, books `fontblack*`/`paper_*`, menu `fontbig24*`/`fontbig36*`, dialog `dialog_*`, diary title `diary_head_*`), decodes the original capitals A–Z from memory (the loaded sprites carry absolute row pointers), measures the capital H and – for the styled families – profile, edge factors and shine, rasterizes the family face at the smallest GDI height whose H reaches the original's (cached per height), puts its H top where the original's is, paints every glyph the original has (ramp in the measured color table's text/edge colors; menu: shine ×2 plus texture; diary title: measured edges), blends partial pixels into the edge tone and replaces the table entry. Slots whose original glyph is a symbol keep it (menu fonts: the arrows in `[`/`]`). A character the face lacks keeps its original glyph (Almendra SC: `… † ‡ ‰ ™ š ž ƒ`; Fondamento and Uncial Antiqua: `ƒ`). Space width from the face; line height per family (`LineHeight` percent or `auto` = at least the original and the ink extent of `bdfhklgjpqyß` + 1: books 12 → 18 and 17 → 25). The pair spacing hook spaces these fonts by their own advance. Rasterizing: GDI, grayscale only (`ANTIALIASED_QUALITY`, `GGO_GRAY8_BITMAP` – never ClearType, independent of the player's smoothing settings). Measured (DE + EN, 1920×1080): all 61 fonts, 7261 glyphs in ~750 ms at startup; every glyph the originals have is replaced (130–131 per interface/books/dialog font, 45 per menu font) except one slot per diary-title font that Almendra SC lacks. Russian edition: not installed, the Cyrillic bitmap fonts stay.
- **Shared style renderer (`src/text/`):** `style.*` holds the measurements (capital H top and height, color profile in 16 steps over the capital height, edge factors per side and distance, brightness across horizontal and vertical stroke runs in five steps, texture strength) and the painters (game ramp; profile with optional contour, fixed gloss, measured edges, shine across the strokes and own value noise) plus the conversion to the game's sprite pixels (partial coverage blended into the family's edge tone, never 0); `gdiface.*` rasterizes a face like the font mode (positive cell height, weight, 65 gray levels; per glyph as a padded coverage mask, smallest height for a given capital H). `ddmod_fontpreview --scene` draws its sheets with the same code (unchanged output); the glyph tables use it from R2 on (`PLAN.md`).
- **Edges and color 0:** without per-pixel alpha the anti-aliased edge must be blended into a fixed tone in advance – exactly what the originals do (black, paper `#9C8E5A`, diary `#947D4A`, Colors); the value 0 is never a visible pixel. The pixel format follows the game's 565/555 global like the GDI ramp (dgVoodoo2 and WineD3D report 565).

## Colors

- **Descriptors:** the GDI branch of the font setup (around `0x496C90`) adds the 61 fonts one by one through an "add descriptor" function (around `0x496670`, `__thiscall` on the font list; stack arguments: two face names, height, text color r, g, b, edge color r, g, b – each byte passed as a dword, `ret 0x24`). The colors are **immediate values in the code**, not data: e.g. white `FF FF FF` on black for `fontn*`, pure yellow `FF FF 00` for `dialog_yellow`, `C8 C8 40` for `fontgo*`, `FF FF 7F` with a gray edge `7F 7F 7F` for the menu capitals, black on gray for the handwriting. The same function is used for the fonts of an optional `fontlist.txt`. A descriptor node (0x44 bytes) keeps the height at `+0x38` and the six color bytes at `+0x3C`–`+0x41`.
- **Conversion:** when the fonts are created (around `0x4958C0`) the descriptor colors are turned into RGB565 levels by `c * 31 / 255` (green `c * 63 / 255`), rounded down, and stored in the font object at `+0x38`–`+0x3D` (text r, g, b, edge r, g, b). So `DE BA 18` arrives one 565 step darker (`#D6B610`).
- **Ramp:** the glyph creation builds a 65-entry ramp per channel, linear from the edge color (gray level 0) to the text color (level 64), packs it as 565 or 555 and maps every glyph pixel's gray level through it; level 0 stays transparent.
- **Bitmap fonts:** every `.fnt` glyph has one flat interior color with edges shaded linearly towards black (fonts for dark backgrounds) or towards the paper tone `#9C8E5A` (handwriting and paper fonts; diary headings towards `#947D4A`); only the menu capitals and diary headings are textured. **23 distinct text colors** in the 61 files: 8 interface colors (5 sizes each), 3 menu variants (normal, highlight, gray; same in both sizes), 4 dialog colors, 1 diary color, 7 inks on paper (`fontblack1` and `fontblack_highlight1` are identical).
- **The mod (`src/fonts/fontcolors.cpp`, `[Fonts] Colors`):** `original` (default) hooks the descriptor function (signature of its first 64 bytes – the first 48 alone also match the `.fnt` loader at `0x496750`; fallback RVA `0x96670`) and replaces the two colors of the n-th call by the colors of the n-th bitmap font, only while each call matches the expected height and game colors (so a `fontlist.txt` or another EXE keeps the game's colors). The table holds the measured colors (interior mode; mean for the textured families) and passes the smallest bytes that survive the rounded conversion unchanged. `game` leaves the game's colors.

## Text fields

- The save dialog's name field handles keys in two places: a **key-down handler** (around `0x4633B0`, virtual keys 0x08–0x2E: Backspace deletes the character before the cursor, Delete, arrows, Home/End, Enter, Esc) and a **character handler** (around `0x4632E0`, `WM_CHAR`), which inserts the character if the font has a glyph for it ("has glyph" check above) and, in name fields, rejects `/ \ ? $ " ! : ; . , < > | * %`.
- Backspace sends both a key-down (deletes) and a `WM_CHAR` 0x08 (insert attempt). The bitmap fonts have no glyphs below 0x20 (checked in all 61 `.fnt` files), so 0x08 is never inserted. A Windows font returns its "missing character" box for 0x08, so the box is inserted and – for a single press – deleted again by the key-down handler; while the key is held, Windows repeats both messages but the key-down handler ignores the repeats, so boxes pile up. Holding Backspace with the bitmap fonts deletes one character only (the game's own behavior).

## Font hook (`src/fonts/fonthook.cpp`, v0.01)

- Hooks `CreateFontIndirectA` and `CreateFontA` (gdi32 exports) in `DllMain` – the only point early enough. Calls from inside `div.exe` get the face of the font chain (`[Fonts] Chain`: Tahoma, else the bundled DejaVu Sans Condensed Bold, `overlay.md`) and the height scaled by `[Fonts] GameFontSize` (percent); weight and the game's colors stay; the charset follows `[Fonts] Charset` (Consequences). Calls from other modules are passed through. `[Features] FontHook=0` switches it off together with the font mode below.
- The chain is resolved on the first hooked call (game thread, not under the loader lock) and logged ("Font chain: using …"). Measured (DE + EN, Windows): main menu and character creation are drawn in Tahoma Bold instead of SimSun; with an unavailable first entry the bundled DejaVu Sans Condensed is loaded and used.
- **Control characters:** the hook also takes `GetGlyphOutlineA`; for calls from `div.exe` with a character byte below 0x20 it returns `GDI_ERROR`, so the game creates no glyph – as with the bitmap fonts – and text fields no longer insert Backspace as a box. With `LogLevel=debug` the same detour feeds the font log ("GDI glyphs of font …").
- **`GameFontSize`** works: glyphs are rasterized from the scaled `HFONT` (150 % gives clearly larger text). The game's layout does not follow because the hook scales only the `HFONT`: the font object's line height `+0x0C`, which the layouts use as line pitch (Layout below), keeps the game's value, so larger text overlaps or gets cut ("…"). The vertical origin uses the same unscaled height.
- **Spacing (`src/fonts/spacing.cpp`):** `[Fonts] Spacing` hooks the pair spacing function (signature of its first 36 bytes, unique; fallback RVA `0x94670`) for GDI fonts only: `font` (default) returns the previous glyph's own advance – the font's designed spacing, no sliding; `game` leaves the game's value; `gap` adds one pixel where the game slid a character closer than its no-touch distance. Bitmap fonts always keep the game's spacing. Measured (DE + EN: load dialog, letter, two books, NPC dialog): `font` shows every period ("71.47 GB", "1.", "2.") and "Lieber" correctly, about as wide as the game's spacing – same line breaks or one word moved, all save names fit; `gap` still hides "2." in the dialog and the foot in "Li" (bottom row, above).

## Font mode (`src/fonts/fontmode.cpp`, v0.01)

`FontHook=1` also switches the game to the GDI path in memory, so `config.lcl` keeps `use8bitfont 1` (as shipped).

- **Reader:** the settings byte `+0x120` (`config-files.md`) is read in exactly one place for the choice of fonts: the font setup function (`0x45BF90`, `__thiscall`, no stack arguments; source `.\BMGUI\Bmgui.cpp`). It first tries to open `fontlist.txt`; with or without that file it reads the byte once and then either loads the 61 `.fnt` files or creates the 61 GDI fonts. The only other reader is the `config.div` writer (below).
- **Timing:** the startup function calls the font setup once (call at `0x40DBD5`), on the main thread and before the game window exists. It reads the byte through the global settings pointer (`0x0065B3D0`), so the configuration is parsed by then. The mod is loaded earlier (ASI loader, `DllMain`).
- **Hook:** a MinHook on the font setup sets the byte to 0 before the original runs and restores the configured value afterwards; the log says "use8bitfont forced to 0 (was 1)". If the settings pointer is still null the call is passed through unchanged.
- **Signature:** the first 34 bytes of the function (`fontmode.h`), ending with `A1 <settings pointer>` and the compare of `+0x120` with 0 – unique in `div.exe`; the settings pointer address is read from the `A1` operand. Fallback RVA `0x5BF90` for the verified build only.
- **Write-back:** on exit the game writes `config.div` (`0x48C6F0`), only keys found in a set at settings `+0x154` – in practice the keys that were in `config.div` (`config-files.md`); `use8bitfont` lives in `config.lcl` and does not end up there. Because the hook restores the byte, even a `use8bitfont` line in `config.div` would be written back with the user's value.
- Measured (DE + EN, Windows): with `use8bitfont 1` in `config.lcl` and `FontHook=1` no `.fnt` file is opened, the main menu is drawn in Tahoma Bold; with `FontHook=0` the original bitmap fonts.

- **Height:** the game passes one cell height per family and every face fills it differently, so each family needs its own height (factor) to match the original's capital height.
- **Line pitch of books and letters is 12 px** (measured on the "Windgeflüster" letter); the bitmap original fills it with almost no ascenders or descenders. Any vector face at the original's capital height touches the neighboring lines ("g" into "fl"); at the largest non-touching size it comes out smaller than the original (GDI height 12–16). The human accepted the touching lines; the pitch is `fontblack1`'s line height `+0x0C`, so an own glyph table can widen it and the page break follows (Glyph table, T1.13-W).

## Consequences

- **All or nothing:** because `use8bitfont` switches all 61 fonts at once, the font mode turns every family into the chain's face (Tahoma Bold). The per-family faces above need the per-family font chain (PLAN.md next steps) and, for the styles, the target text renderer – an own glyph table per font (Glyph table, above) gives both per font without the GDI path.
- **Code page:** the character is passed to `GetGlyphOutlineA` as a *signed* `char`, so bytes ≥ 0x80 (umlauts, accents, Cyrillic) arrive sign-extended. German umlauts and ß of the main-menu hint arrive as the correct characters (font log). The game asks for `ANSI_CHARSET` (0), so GDI maps the bytes through code page 1252. Measured in the Russian version (1.0061, `use8bitfont 0` set by hand, `game-version.md`): the 1251 bytes come out as Latin-1 letters ("ÍÎÂÀß ÈÃÐÀ"). **Setting `lfCharSet = RUSSIAN_CHARSET` (204) in the font hook is enough** – GDI then maps the same bytes through code page 1251 and the main menu shows correct Cyrillic in Tahoma Bold. The hook does this via `[Fonts] Charset` (`auto` = 1251 for the Russian EXE hash, otherwise the game's charset; `1252`/`1251` force it). The font mode does not run on 1.0061 (best effort, no RE on that EXE), so the Russian version keeps its Cyrillic bitmap fonts unless `use8bitfont 0` is set by hand.
- **Proton:** SimSun is a Windows font; under Proton the game's request is substituted by Wine – one more reason for the hook. Whether Proton's own Tahoma is found by the chain shows in the Deck log (step 7): for an installed face the chain logs its English full name (from the font's `name` table, ID 4 – GDI's metrics give the UI-language name, "Tahoma Fett" on a German Windows) and the file the registry font list (`HKLM`/`HKCU` `…\Windows NT\CurrentVersion\Fonts`, value name "<full name> (TrueType)") names for it; on Windows "Tahoma Bold" = `C:\Windows\Fonts\tahomabd.ttf`.
- **Overlay:** the game offers no GDI-on-surface path to reuse; the overlay's text approach is decided in `overlay.md`.
