# File formats

Our own descriptions of Divine Divinity's data formats.

## ML_FONT_01 (fonts)

Bitmap fonts in `fonts/*.fnt` (`use8bitfont 1`), identical in the German and English copy. The Russian edition ships its own files in code page 1251 order (e.g. `dialog_white`: all 64 slots 0xC0–0xFF filled = А–я, 159 glyphs instead of 122). 61 files, but only **five typefaces** – one file per size **and color** (colors are baked in, edge pixels differ slightly between color variants):

| Family | Files | Sizes (line height) | Characters | Look / probable source typeface |
|---|---|---|---|---|
| Dialog text | `dialog_white/_yellow/_red/_grey` | 15 px | full Latin-1 | bold humanist sans; **Tahoma Bold** (or Verdana Bold) – pixel comparison: Tahoma Bold 13 px matches width and shapes best, Verdana Bold is clearly wider; Verdana Pro (suggested by font matchers) only appeared in 2017 |
| Interface (small caps) | `font{n,go,yel,gr,or,gra,red,b}{1-5}` – 8 colors × 5 sizes | 13, 13, 12, 10, 9 px | capitals; lowercase are small capitals | flared sans small caps; probably **Lithos** (Black/Bold, Carol Twombly, Adobe 1989) |
| Handwriting (books, letters) | `paper_green/_red` (+`_high`), `fontblack2`, `fontblack_highlight2`; `fontblack1`, `fontblack_highlight1` | 17 px; 12 px | full Latin-1 | broad-nib script; probably **Ondine** (Adrian Frutiger 1954, Adobe/Linotype) |
| Menu capitals | `fontbig24`/`fontbig36` (+`gray`, `highlight`) | 23, 35 px | capitals, digits, umlauts, `ß` | Lombardic/uncial capitals; source typeface not found |
| Diary headings | `diary_head_640/_800/_1024` | 24, 31, 38 px | capitals (no `X`, only `x`), digits, umlauts | blackletter capitals, textured; probably **Vinque** (Ray Larabie, Typodermic, around 2000) |

Source typefaces were identified by the human from the character sheets (WhatTheFont, Font Matcherator); the files themselves name no typeface. Character sheets and the full overview are generated by `tools/fontpreview` (CLAUDE.md). Reader: `src/overlay/fnt.cpp`; all integers little endian.

| Offset | Type | Meaning |
|---|---|---|
| 0x00 | 10 bytes | `ML_FONT_01` |
| 0x0A | u32 | table size (256) |
| 0x0E | u32 | line height in pixels (e.g. 15 for `dialog_*`, 13 for `fontn1`) |
| 0x12 | u32 | number of glyphs in the file |
| 0x16 | 256 × i32 | glyph table indexed by character byte (code page of the language version): record offset relative to **0x26**; 0 = no glyph, negative = alias of the glyph at the absolute value |

Each glyph is a 16-byte prefix followed by the record:

Prefix and record together are exactly the game's in-memory glyph followed by its sprite (`glyph-layout.md`) – the loader uses them in place.

- Prefix: 8 bytes `32 54 76 98 CC DD EE FF` (same in every glyph; the slot of the GDI black-box size, unused for bitmap fonts), i32 origin x (0), **i32 = minus the glyph's top row** relative to the top of the line (origin y; e.g. −3 for capitals, −5 for lowercase, −11 for `.` in `dialog_white`).
- Record: i16 advance, i16 vertical advance (0), u16 character code, then the sprite: u32 size (= next field + 2 × pixel count), u32 offset of the pixel block (= 12 + size of the row table), u16 width, u16 height; then one row entry per pixel row – u16 span count *n*, u32 byte offset of the row's first pixel in the pixel block, *n* × (u16 x, u16 length), u16 *n* again; then the pixel block: RGB565 values of all spans, row by row; then one padding byte.
- Pixels outside spans are transparent. The colors are pre-shaded (anti-aliased edges darkened towards black), so the glyphs are made for dark backgrounds.
- There is no space glyph (entry 0) and no space width in the header – the game then uses a built-in space of **6 px** for every bitmap font. There is no kerning table; the game spaces each pair by sliding the glyphs together (`text-rendering.md`, pair spacing).

## Localized texts (`localizations\<language>\text.cmp`)

Loaded at startup by the text loader (`text-rendering.md`, Text table); `dat\global.cmp` has the same strings too (not traced). All integers little-endian.

- u32 section count (6 in DE/EN/FR), then per section: u32 section type (menu and interface texts: 10000), i32 entry count (negative = the section's strings are 16-bit characters).
- Per entry: u32 id, then two strings, each u32 length *n* followed by *n* + 1 characters including the terminating NUL (nothing at all for *n* = 0). The second string is empty for the menu texts.
- Code page of the 8-bit strings: 1252 (DE/EN/FR). Menu labels are in capitals (e.g. DE id 335 and 374 "HINTERGRUNDGERÄUSCHE", 377 "3D SCHATTEN", 378 "NEBEL"); `ddmod_fontpreview --labels` lists them with their widths.

## Hero sprites (`static/heroes/<class><gender><sheet>.bic|.idc`, `<class><gender>.key`)

Status: index structure understood, image data not decoded yet (2026-10-18).

- `.key` – text, CRLF. First line `Max size W,H` (largest frame). Then one line per animation: `NAME,first,end` – frame range `[first, end)` in the `.idc`/`.bic` of the sheet whose letter is the **third character** of the name (e.g. `MAC…` → sheet `C`). Names start with `M`; the second character selects the action, the fourth the variant.
- `.idc` – frame index, **40 bytes per frame**, little endian:

| Offset | Type | Meaning |
|---|---|---|
| 0x00 | u32 | offset of the frame data (in the decompressed `.bic` stream) |
| 0x04 | u32 | size of the frame data |
| 0x08 | u16 | width |
| 0x0A | u16 | height |
| 0x0C | i16 | hotspot x |
| 0x0E | i16 | hotspot y |
| 0x10 | 24 bytes | unknown; all `FF` in sheets A and E, varies in B–D (attachment points?) |

  Frames are stored back to back (offset + size = next offset). The indexed total is about twice the `.bic` file size → the `.bic` file is compressed again as a whole or in blocks.
- `.bic` – compressed frame data, 16-bit pixels with skipped transparent areas (assumed, see `graphics-assets.md`).

## Image lists (`static/imagelists/`)

Status: index entry size known only (2026-10-18).

- `CPackedi.<n>c` – index, **56 bytes per image**; starts with u32 data offset, u32 width, u32 height, followed by further fields (width-1, height-1, hotspot, …). 13 lists, 98 761 images.
- `CPackedb.<n>c` – compressed image data; begins with the same kind of stream header as the hero `.bic` files.
- `apackedi.<n>` / `APackedb.<n>` – 16-byte entries, probably animation tables; `Collide.<n>` – collision data; `roofs.000` / `roofs.dat` – roof images and their table.

**External reference – Divinity_Graphics_Extender** (Raanar, v0.01, `github.com/Raan/Divinity_Graphics_Extender`, published 2026-10-22): C#/WPF tool that exports and imports sprites of `CPackedi`/`CPackedb.*c` for Divine Divinity and Beyond Divinity. Only a README and a binary – no source code, no license; we neither download the binary nor take anything from it, it only shows that the format is decodable and re-encodable. Its stated limits fit our findings: the image size cannot change on import, and there is no semi-transparency (the sprite format has no per-pixel alpha, `glyph-layout.md`).
