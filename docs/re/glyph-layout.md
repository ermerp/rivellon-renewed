# Glyph table, drawing, layout and colors

How the game stores, draws and lays out glyphs for `.fnt` and GDI fonts alike, and where the text colors come from. Font paths: `text-rendering.md`; the mod's glyph renderer: `fonts-mod.md`. Addresses: verified 1.0062A `div.exe` (`game-version.md`).

## Font object, glyph and sprite

Both font kinds end in the same structures, so everything here holds for `.fnt` and GDI fonts alike. This is the basis for the target text renderer (`docs/decisions.md`).

- **Font object** (0x44 bytes, constructor around `0x493A30`): `+0x00` GDI part (null for `.fnt`), `+0x04` pair-spacing cache (64 KB, `0xFF` = not computed), `+0x08`–`+0x13` the 12 header bytes of the `.fnt` file (table size, **line height at `+0x0C`**, glyph count; GDI: `+0x0C` = the game's `lfHeight`), `+0x14` table of 256 glyph pointers, `+0x18` the `.fnt` file block (null for GDI), `+0x1C` a built-in space glyph, `+0x2C` **space width** (i16), `+0x34` flag "store GDI glyphs as full rectangles" (0), `+0x38`–`+0x3D` colors, `+0x3E` text-field cursor color (u16), `+0x40` layout variant flag copied from settings `+0x130` (a second set of the same measure/draw functions; it changes only how lines are cut).
- **`.fnt` loading** (around `0x493D50`; the function at `0x496750` only queues the file name, the files are opened when the font list is turned into font objects around `0x4958C0`): checks `ML_FONT_01`, copies the header into `+0x08`, reads the rest of the file as one block into `+0x18`, uses the block's first 1 KB directly as the glyph table and turns every offset into a pointer (aliases into the pointer of the glyph they name). Each **glyph record in the file is already the in-memory glyph** (layout below, `file-formats.md`); the loader only turns the sprite's row offsets into pointers. No pixel conversion – the pixels stay RGB565 as stored. If the file has no space glyph, entry 0x20 points to the built-in one and the space width is set to **6 px** for every bitmap font. A second, older loader (fixed 224 glyphs from 0x20, 20-byte metrics) handles files without the `ML_FONT_01` tag; none of the shipped files uses it.
- **Glyph** (both kinds): `+0x00`/`+0x04` black-box width/height (GDI only; in `.fnt` files these 8 bytes are the constant marker and unused), `+0x08` origin x, `+0x0C` origin y (the glyph is drawn at pen y minus this value; `.fnt` stores minus the top row, GDI the font ascent shifted so that the baseline lies at line top + `+0x0C` − 1), `+0x10` advance (i16), `+0x12` vertical advance (i16, 0), `+0x14` character code (i16), `+0x16` **sprite**.
- **Sprite** (the game's general 2D sprite format, also used for its other images): u32 total size, u32 offset of the pixel block, u16 width, u16 height, one row entry per row (span count, pointer to the row's first pixel, spans of x and length, span count again), then the RGB565/555 pixels of all spans. Pixels outside the spans are transparent; there is **no per-pixel alpha**. The GDI path builds it from a full 16-bit rectangle in which the value 0 means transparent (a converter around `0x559750` packs the non-zero runs; a second one around `0x5587F0` makes one full span per row), and it maps any glyph pixel that would come out as 0 to 1 so that it stays visible.
- **Lifetime:** the font destructor (around `0x493B20`) frees only the file block for a `.fnt` font (the glyphs live inside it); for a GDI font it frees every table entry except the space and the table itself, with the game's heap. Fonts are created once at startup.
- **Drawing:** a character is drawn at pen x + origin x, pen y − origin y by queueing its sprite with the renderer's sprite container (`DllSlashedGetInfo(0)`, `CSpriteContainerImp`, vtable `+0x28`: sprite, x, y, a sort value and flags). The container collects the requests in a list (`COverlay` in `slash1.dll`, 32 bytes per entry), sorts it and draws it at the end of the frame. The request is dropped only if the sprite lies completely off screen – a glyph is **not clipped to its line**. Per-sprite flags exist (a sibling method sets a fixed 50 % translucency for one flag bit); per-pixel blending does not. A second path (around `0x494580` → `0x556A80`) copies the span pixels opaquely into a 16-bit buffer, clipped to the buffer – used for panels the game pre-renders with text and then turns into one sprite (e.g. around `0x523D00`).
- **Nothing above the line top in menu entries and the diary title (T1.17-W):** own glyphs whose ink reaches above the top of their line (origin y > 0) lose exactly those rows in the main menu and its pages (`fontbig24*`/`fontbig36*`: umlaut dots of "ZURÜCK", "ÜBERNEHMEN", the ascenders of Uncial Antiqua's d, h, k, l) and in the diary title (`diary_head_*`: the Ä's dots). The sprite container itself drops only sprites that lie completely off screen (`slash1.dll`, its `+0x28` method checks the screen size only), so the cut comes from the game side – probably these texts go through the buffer path above, whose buffer starts at the line top (not traced further). The original bitmap fonts never reach above the line top (every glyph's top row ≥ 0, `fontbig36` capitals from row 2, diary capitals from row 3–4). The mod keeps the ink below it (`[Family.*] TopFit`). How much room there is: `fontbig36` capitals start at row 2, `diary_head_1024` at row 4 – Uncial Antiqua's d/h/k/l and Ü reach 7 px above that (its left Ü dot touches the U's arm), Almendra SC's Â/Ê/Î/Ô/Û 6 px and its Ä 3 px after moving close. The French texts use no accented capitals at all (`hints.txt`, `skills.txt`: none, against 2000+ accented lowercase letters; capital-only words in `text.cmp` such as "QUETES", "OPTIONS", "RETOUR" without accents – the file is partly binary, so not every string was checked), so in French only lowercase accents ever appear on screen.
- **Layout:** measuring and line breaking (around `0x494DC0`, `0x495260`, `0x495380`, `0x494F50`) add the pair spacing (or the advance) per character and the space width `+0x2C` per space; nothing reads a glyph's height. The **line pitch comes from the font's `+0x0C`**, read directly by the callers: several list and text views use `+0x0C` + 1 (the largest of the fonts involved, around `0x4F1170`, `0x4F6AC0`, `0x4F6EF0`, `0x4F7230`, `0x4F8540`), others add `+0x0C` per line (around `0x470800`, `0x51A170`, `0x55F030`), and some panels size themselves as lines × `+0x0C` plus a margin (around `0x523040`, `0x530AB0`). A text line is skipped only when its y is more than two line heights outside the target.

**Consequences for own glyphs:**

- **Larger glyphs are possible:** the sprite size is free, drawing does not clip to the line, and line breaking follows the real advances, so wider text wraps earlier and panels sized by line count grow. Vertically, neighbors overlap unless `+0x0C` grows too; raising `+0x0C` widens the pitch wherever the layout reads it (and moves the GDI baseline, but not the origin of an own glyph). Measured (T1.13-W, DE + EN): the load list, letters and books take the wider pitch, and the reading window's **page break follows** – the text simply spreads over more pages.
- **Ways to feed own glyph data:** (1) the GDI path as now – one face per font, colors only as the two-color ramp; (2) answering `GetGlyphOutlineA` with own coverage – any rasterizer, but still the two-color ramp; (3) **an own glyph table:** after a font object is created, replace all 256 table entries with own glyphs (own origin, advance, sprite in full 16-bit color per pixel) and set `+0x0C` and `+0x2C` as needed. (3) carries every style (color profile, rim, gloss across the strokes, texture) and works with the bitmap path as shipped (`use8bitfont 1`): no GDI font, no font mode, no SimSun or Proton font substitution, the code page decides only which character goes into which byte slot. In the bitmap path the destructor frees only the file block, so the own glyphs stay the mod's memory; in the GDI path the game would free them with its own heap.
- **Edges and color 0:** without per-pixel alpha the anti-aliased edge must be blended into a fixed tone in advance – exactly what the originals do (black, paper `#9C8E5A`, diary `#947D4A`, Colors); the value 0 is never a visible pixel. The pixel format follows the game's 565/555 global like the GDI ramp (dgVoodoo2 and WineD3D report 565).

## Colors

- **Descriptors:** the GDI branch of the font setup (around `0x496C90`) adds the 61 fonts one by one through an "add descriptor" function (around `0x496670`, `__thiscall` on the font list; stack arguments: two face names, height, text color r, g, b, edge color r, g, b – each byte passed as a dword, `ret 0x24`). The colors are **immediate values in the code**, not data: e.g. white `FF FF FF` on black for `fontn*`, pure yellow `FF FF 00` for `dialog_yellow`, `C8 C8 40` for `fontgo*`, `FF FF 7F` with a gray edge `7F 7F 7F` for the menu capitals, black on gray for the handwriting. The same function is used for the fonts of an optional `fontlist.txt`. A descriptor node (0x44 bytes) keeps the height at `+0x38` and the six color bytes at `+0x3C`–`+0x41`.
- **Conversion:** when the fonts are created (around `0x4958C0`) the descriptor colors are turned into RGB565 levels by `c * 31 / 255` (green `c * 63 / 255`), rounded down, and stored in the font object at `+0x38`–`+0x3D` (text r, g, b, edge r, g, b). So `DE BA 18` arrives one 565 step darker (`#D6B610`).
- **Ramp:** the glyph creation builds a 65-entry ramp per channel, linear from the edge color (gray level 0) to the text color (level 64), packs it as 565 or 555 and maps every glyph pixel's gray level through it; level 0 stays transparent.
- **Bitmap fonts:** every `.fnt` glyph has one flat interior color with edges shaded linearly towards black (fonts for dark backgrounds) or towards the paper tone `#9C8E5A` (handwriting and paper fonts; diary headings towards `#947D4A`); only the menu capitals and diary headings are textured. **23 distinct text colors** in the 61 files: 8 interface colors (5 sizes each), 3 menu variants (normal, highlight, gray; same in both sizes), 4 dialog colors, 1 diary color, 7 inks on paper (`fontblack1` and `fontblack_highlight1` are identical).
